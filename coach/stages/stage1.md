# 阶段 1：全栈骨架上线

**你的角色**：全栈工程师、运维。

**目标**：F0。一个只会「注册、登录、新建目标、看列表」的空壳，但它是完整的：有数据库、有接口、有页面、有 CI、部署在你自己的域名上，走 HTTPS。

**完成后简历上可以写**：基于 FastAPI、PostgreSQL、React 独立完成前后端开发，使用 Docker Compose 与 Caddy 部署上线并配置 HTTPS，搭建 GitHub Actions 持续集成。

这是全栈知识最密集的一个阶段。分四个任务，每个任务一个分支、一个 PR。

## 先学再做：建立你的判断标准

这个阶段有四个钩子，每个任务之前做一个。资料和「只看哪几节」在 `docs/RESOURCES.md`。

| 在哪个任务之前 | 钩子 | 时间 | 写入 | 对照组里看什么 |
| --- | --- | --- | --- | --- |
| 任务 1 | H1a 协作规范 | 30 分钟 | `coach/standards/workflow.md` | 官方模板的 CI 文件 |
| 任务 2 | H1b 后端与数据 | 2.5 小时 | `coach/standards/backend.md` | 官方模板的 `items.py`、`deps.py`、`test_items.py` |
| 任务 3 | H1c 前端 | 3 小时 | `coach/standards/frontend.md` | 官方模板的 `login.tsx` 和 `src/` 目录分法 |
| 任务 4 | H1d 部署 | 2 小时 | `coach/standards/deploy.md` | 官方模板的部署说明，和你脚手架的部署文档 |

每个任务的顺序都是：看资料、写标准、写设计说明、教练写代码、你说「审查」、合并。

任务 1 有一个现成的审查练习：用你刚写的 `workflow.md` 去看脚手架那 4 个遗留问题。如果当时每次提交都跑 CI，哪几个会被拦住？剩下的要靠什么才能发现？

## 任务 1：让脚手架在干净环境里跑起来（分支 `fix/scaffold-clean-env`）

- 教练做：修 `docs/REFERENCE_MAP.md` 里列的 4 个遗留问题；本地用开发模式的 compose 起来；执行迁移；确认健康检查接口和接口文档页能打开。
- 你做：看教练的每处改动，说出它为什么能修好；看 CI 从红变绿。
- 新概念：Docker、Compose、环境变量、CI。
- 验收：`docker compose` 起来后所有容器健康；CI 绿。

## 任务 2：目标的新建和列表（分支 `feat/goal-crud`）

- 你先写设计说明 `coach/designs/stage1-goal.md`：
  1. goals 表需要哪些字段？每个字段是什么类型、能不能为空？
  2. 目标有哪几种状态？现在先实现哪几种？
  3. 一个用户能看到别人的目标吗？在哪一层保证？
  4. 新建目标的接口，请求里要传什么，返回什么？
- 教练做：按 `docs/REFERENCE_MAP.md` 的样板表，逐层写 model、迁移、schema、service、api、登记路由、测试。每写一层停一下，让你说出这一层的职责。
- 你亲手做：goals 表的字段设计；亲手写「没登录时访问返回 401」这个测试。
- 新概念：HTTP 接口、三层架构、ORM、迁移、JWT。
- 验收：在接口文档页上能登录、新建目标、查列表；用另一个账号看不到；测试通过。

## 任务 3：前端的登录页和目标列表页（分支 `feat/frontend-skeleton`）

- 教练做：在 `frontend/` 用 Vite 创建 React + TypeScript 项目，配 Tailwind；配开发代理把 `/api` 转给后端；写登录页和一个发请求的封装；在 CI 里加前端构建。
- 你亲手做：读懂登录页后，参照它自己改出目标列表页（教练可以提示，不能替你写完）。
- 新概念：组件、状态、发请求、令牌存哪。
- 验收：浏览器里登录后看到目标列表，能新建，刷新后还在，退出后回到登录页。

## 任务 4：部署上线（分支 `chore/deploy`）

- 你先写设计说明 `coach/designs/stage1-deploy.md`：
  1. 服务器买在哪个地区？为什么？（看 `docs/PITFALLS.md` 的部署部分）
  2. 哪些端口对公网开放，哪些只给本机？
  3. 生产环境的密钥怎么生成、放在哪？
  4. 以后更新版本，步骤是什么？
- 教练做：按 `deploy/README.md` 给出逐条命令清单，每条写明在干什么；按你的域名写好 Caddy 配置。
- 你亲手做：买服务器和域名；配域名解析；登录服务器，自己敲每一条命令。教练不接触服务器和密钥。
- 新概念：域名与 DNS、反向代理、HTTPS、防火墙。
- 验收：见下。

## 阶段验收

1. 用手机流量（不连家里网络）访问 `https://你的域名`，能注册、登录、新建目标。
2. 浏览器地址栏有锁的标志。
3. 在服务器上重启全部容器后，之前建的目标还在。
4. 数据库和 Redis 的端口从公网连不上。
5. main 分支的 CI 是绿的，四个 PR 都有记录，每个 PR 的描述里有你按标准做的审查结论。
6. 「讲一遍」：一个新建目标的请求从手机到数据库的完整路径。

## 搞坏实验

- 本地停掉数据库容器，看接口报什么错，再启动看能否恢复。
- 故意写一个会失败的测试推上去，看 CI 怎么拦住你，再修好。
- 把请求里的令牌改掉一个字符，看返回什么。
- 在服务器上只停 Caddy，看浏览器是什么表现；只停接口容器，又是什么表现。

## 口述检查题

1. 讲一个新建目标的请求经过的每一站。
2. 三层各管什么？goal 的「只能看自己的」写在哪层？
3. 迁移文件是什么？不用它直接改数据库会有什么后果？
4. 本地和服务器上跑的是不是同一套东西？靠什么保证？
5. Caddy 在这里做了哪两件事？
6. 脚手架那个缺依赖的问题，为什么你原来的电脑上没暴露？

## 预想卡点

见 `docs/PITFALLS.md` 的起步、后端、前端、部署四节。最常见的三个：迁移没执行、路由没登记、域名解析没生效就去申请证书。
