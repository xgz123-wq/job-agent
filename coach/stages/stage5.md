# 阶段 5：评测与交付

**你的角色**：测试、项目负责人。

**目标**：F7。拿出数字，把项目整理成能交给别人看的样子。

**完成后简历上可以写**：构建了 15 个任务的评测集，覆盖调研、长程恢复与注入攻击场景；任务完成率从 X% 提升到 Y%，断点恢复成功率与审批拦截率均为 100%。

## 先学再做：建立你的判断标准

动手之前先花约 2 小时。资料和「只看哪几节」在 `docs/RESOURCES.md` 的 H5。

1. **看**：带 ★ 的必看，其余选看。
2. **写**：把你的标准写进 `coach/standards/evals.md`，五条以内，每条配一个反例。
3. **对照**：这个阶段没有外部对照组。对照物是你自己的第一轮和第二轮数字。
4. **审查**：教练做完后说「审查」，用你的标准逐条检查它的产出。

这个阶段还要做一件事：把 `coach/standards/` 里九个文件从头看一遍，每个文件挑一条你最初写错或写浅了、后来改掉的标准。这九条就是你判断力成长的证据，写进 `docs/INTERVIEW.md`。


## 你要写的设计说明

`coach/designs/stage5-evals.md`：

1. 每类任务的「完成」怎么判定？哪些能自动判，哪些要人看？
2. 15 个任务具体是哪些？
3. 失败怎么归到四类之一：工具失败、规划错误、上下文丢失、终止判断错误？
4. 哪些是硬指标，哪些是越高越好？

## 教练要做

1. 把你写的 15 个任务填进 `evals/tasks.yaml`，写评测脚本，输出汇总表。
2. 跑第一轮得到基线，和你一起归因，改最多的那一类，跑第二轮。
3. 重写 `README.md`：一句话介绍、线上地址、架构图、和 Muse 的对照、如何本地运行、评测结果、已知局限。
4. 工程收尾：数据库定时备份；日志保留策略；一个只读的演示账号。
5. 检查仓库：没有密钥，没有个人简历原文。

## 你亲手做的事

- 写 15 个任务。
- 人工判定至少 5 个任务的结果，和自动判定对比。
- 写三个失败案例分析，放进 `docs/INTERVIEW.md`。
- 录一段 3 分钟演示：新建目标、实时步骤、重启恢复、收到通知、审批拦截。
- 把 `docs/INTERVIEW.md` 所有问题填完。
- 做一次 20 分钟的模拟面试。

## 验收

1. 一条命令跑完评测集并输出汇总表。
2. 有两轮数字，能说清第二轮为什么变了。
3. 断点恢复成功率和审批拦截率都是 100%。
4. 一个没见过项目的人，看 README 3 分钟内明白它是什么、怎么打开。
5. `coach/LEARNER.md` 里全栈和智能体两张表，大部分达到 2 级以上。

另外：`coach/standards/evals.md` 已写好，九个标准文件都有审查记录。

## 口述检查题

1. 完成率是多少？怎么算的？
2. 讲一个失败案例：现象、归因、怎么改、数字变了多少。
3. 这个评测集有什么局限？
4. 线上数据丢了怎么恢复？
5. 再给你两周，先做什么？

## 预想卡点

| 卡点 | 对策 |
| --- | --- |
| 不知道怎么自动判报告质量 | 先只自动判「完成了没、有没有来源、花了多少」。质量用人工抽查 |
| 完成率低，不好意思写 | 低的数字加清楚的归因和改进，比没有数字强得多 |
| 评测跑一次太贵 | 用便宜的模型跑全量，好模型抽几个对比 |
| 想继续加功能 | 先完成这 5 条验收，再看待办 |
