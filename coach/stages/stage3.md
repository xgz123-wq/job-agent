# 阶段 3：长程

**你的角色**：Agent 工程师。

**目标**：F2 断点续跑、F3 定时盯岗位、F4 主动通知。这是「长程智能体」这个名字成立的地方。

**完成后简历上可以写**：设计了目标、任务、步骤三层状态机，支持 worker 中断后从断点恢复且不重复执行已完成步骤；基于 Celery beat 实现定时目标与心跳调度，并设计通知门槛避免无效打扰。

## 先学再做：建立你的判断标准

动手之前先花约 2 小时。资料和「只看哪几节」在 `docs/RESOURCES.md` 的 H3。

1. **看**：带 ★ 的必看，其余选看。
2. **写**：把你的标准写进 `coach/standards/reliability.md`，五条以内，每条配一个反例。
3. **对照**：在 GitHub 上看最新版 nanobot 的 `nanobot/session/recovery.py`，找出它恢复任务时先检查什么。
4. **审查**：教练做完后说「审查」，用你的标准逐条检查它的产出。

## 你要写的设计说明

`coach/designs/stage3-state.md`：

1. 目标和任务各有哪几种状态？画出能怎么转换，不能怎么转换。
2. 每一步存哪些信息，才够重启后接着做？
3. 重启后发现某一步「开始了但没记录完成」，重做、跳过还是问用户？对搜索和对发邮件，答案一样吗？
4. 一个任务失败了，它所属的目标怎么办？重试几次？

`coach/designs/stage3-schedule.md`：

7. 「实质新进展」怎么定义？什么一定通知，什么一定不通知？
8. 没有新内容时，要不要调用模型？

## 教练要做

1. 状态机：状态转换集中在一个 service 里，非法转换直接报错。
2. 步骤带唯一编号，执行前先查是否已完成。
3. 恢复逻辑：worker 启动时找出「运行中但没人管」的任务并接上。
4. beat 定时扫描到期的定时目标并投递任务。
5. 已推送岗位的去重。
6. 邮件通知，加网页上的未读标记。
7. 技能文件 `app/agent/skills/job-watch.md` 初稿。
8. 目标列表页显示真实状态和下次运行时间。

## 你亲手写的判断函数

- `can_transition(current, target) -> bool`：这个状态转换合不合法。
- `next_action_on_resume(step) -> str`：返回 `"redo"`、`"skip"` 或 `"ask_user"`。
- `should_notify(result, history) -> tuple[bool, str]`：值不值得通知，并给出原因。

## 新概念

状态机、幂等、Celery beat。

## 验收

1. 线上跑一个调研任务，中途在服务器上重启 worker 容器。任务从断点继续，steps 表里没有重复的步骤编号。
2. 建一个间隔 2 分钟的定时目标，按时触发，收到邮件。
3. 同样条件再触发一次，没有新内容，不发邮件。
4. 目标列表页的状态和下次运行时间是对的。
5. 让它连续跑 3 天，没有重复推送。

另外：本阶段的标准文件已写好，并且做过至少一次「审查」和一次「二选一」，结论记在 PR 里。

## 搞坏实验

- 在不同时刻重启 worker，至少 5 次，每次都正确恢复。
- 把 `should_notify` 改成永远返回 True，体会被打扰的感觉，再改回来。
- 手动把数据库里一个任务的状态改成非法值，看系统怎么反应。

## 口述检查题

1. 画出状态机，讲每条转换什么时候发生。
2. worker 在「工具执行完但还没记录」的瞬间挂了，重启后会怎样？你怎么处理？
3. 「幂等」是什么意思？你的哪些步骤是幂等的，哪些不是？
4. beat、队列、worker 三者是什么关系？
5. 你的通知门槛是什么？各举一个通知和不通知的例子。
6. 同时有三个目标在跑，现在的设计撑得住吗？

## 预想卡点

| 卡点 | 对策 |
| --- | --- |
| 状态机不知道怎么画 | 先只画排队、运行中、完成三个，跑通后再加 |
| 重复执行的问题绕不清 | 这是本阶段最难也最值得讲的点。专门用一次会话只讨论它，记进卡点记录 |
| 邮件发不出去 | 邮件服务的配置是杂务，让教练处理；本地可以先用假邮件服务看效果 |
| 3 天验收太久 | 前 4 条通过就可以进阶段 4，第 5 条在后台继续跑 |
| 搜不到岗位信息 | 先用手动贴链接的方式，或把目标换成「盯某几家公司的招聘页」 |
