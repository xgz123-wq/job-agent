# 开发规范

这些是企业里的普遍做法。从第一天就照做，不是为了形式，是为了面试时能说「我的项目是按这套流程做的」，并且拿得出记录。

## 分支与提交

- `main` 永远是能上线的状态。不直接往 main 提交。
- 每个任务开一个分支：`feat/goal-crud`、`fix/utils-imports`、`docs/architecture`。
- 提交信息格式：`类型: 做了什么`。类型用 `feat`（新功能）、`fix`（修问题）、`docs`、`test`、`refactor`（不改行为的整理）、`chore`（杂务）。
- 一个提交只做一件事。

## PR（合并请求）

- 分支推上去后开 PR，按模板填写。即使只有你一个人，也走 PR：它留下了「为什么改」的记录。
- CI 是绿的才合并。
- 合并后删除分支。

## 完成的定义

一个任务算做完，需要同时满足：

1. 本地跑通。
2. 有测试，CI 通过。
3. 改了表结构的话，带了迁移。
4. 你能讲清它做了什么。
5. 有设计决定的话，记进了 `docs/DECISIONS.md`。

## 后端分层

沿用脚手架的规则（详见 `backend/CLAUDE.md`）：

- `api`：收请求、校验参数、验身份、调用 service、返回统一格式。
- `services`：业务逻辑，不碰 HTTP。
- `models`：数据表，只有 service 能调。
- 不跨层，不反向依赖。

智能体代码在 `app/agent/`，它被 service 和 Celery 任务调用，自己不直接处理 HTTP。

## 数据库

- 改表结构只通过 Alembic 迁移，不手动改库。
- 迁移文件要提交。
- 上线流程里有一步是执行迁移。

## 配置与密钥

- 所有配置走环境变量，在 `app/core/config.py` 里声明。
- `.env` 不进 git。`.env.example` 进 git，只写变量名和假值。
- 密钥不写进代码、日志、提交信息，也不发给模型。
- 密钥泄露了：立刻去服务商那里作废并换新的。

## 测试

- 每个接口至少一个测试：正常情况一个，没登录的情况一个。
- 判断函数（`should_stop` 之类）每个分支都要测到。
- 慢测试标 `@pytest.mark.slow`，CI 默认不跑。

## 日志

- 用脚手架的日志配置，不用 `print`。
- 智能体的每一步都要落到 `steps` 表，这是排查问题和做评测的依据。
